== Bloque 1 · La plataforma: OpenShift AI

=== ¿Qué es Red Hat OpenShift AI?

Una plataforma de IA/ML *sobre OpenShift*: capacidades para todo el ciclo de vida, gestionadas con operadores y recursos declarativos.

[cols="1,1", options="header"]
|===
| Capacidad | Qué aporta
| *Desarrollar* | Workbenches: entornos Jupyter listos para data scientists
| *Entrenar* | Training: entrenamiento y fine-tuning, incluido distribuido
| *Servir* | Model serving: endpoints de inferencia (KServe, llm-d)
| *Operar* | Pipelines y monitoring: flujos reproducibles y visibilidad
|===

* El `DataScienceCluster` declara *qué componentes se activan*: la plataforma es modular.

=== El cluster: componentes activos

El `DataScienceCluster` (DSC) declara los componentes; cada uno aporta una capacidad:

[cols="1,1", options="header"]
|===
| Componente | Capacidad
| *Dashboard* | Acceso unificado a la plataforma
| *Workbenches* | Desarrollo: entornos Jupyter
| *Serving* | KServe + llm-d: endpoints de inferencia
| *Monitoring* | Métricas y dashboards de la plataforma
|===

* Piezas de infra que la plataforma aprovecha: *NVIDIA GPU Operator* (hace la GPU consumible por los pods), *Gateway API* (routing estándar), *Authorino* (auth).
* En este cluster: OpenShift AI 3.5 · 1 GPU L4 · modelo pre-desplegado.

=== Cómo la plataforma habilita el mundo agéntico

[source,text]
----
 AGENTE ── necesita ──▶ modelo servido ─────▶ Serving (KServe / llm-d)
                    ├─ cómputo ──────────────▶ GPU Operator + L4
                    ├─ acceso controlado ────▶ Gateway / MaaS + Authorino
                    └─ visibilidad ──────────▶ Monitoring / OpenTelemetry
----

* El "cerebro" es un *endpoint servido* por la plataforma, no un binario local.
* El cómputo es un *recurso de cluster*: la GPU, gestionada por el operator.
* El acceso se *controla* con gateway, auth y cuotas — y todo lo que ocurre queda *observable*.
* **OpenShift AI pone la infraestructura; el agente es quien la consume.**

== Bloque 2 · Agentes y skills

=== De chatbot a agente

[cols="1,1,1,1", options="header"]
|===
| | *Chatbot* | *Copilot* | *Agente*

| ¿Quién decide el siguiente paso?
| El humano
| La herramienta (con sugerencias del LLM)
| *El LLM*

| ¿Ejecuta acciones?
| No, solo texto
| Dentro de una app
| *Sí*: herramientas reales

| ¿Cuándo para?
| Tras cada respuesta
| Tras cada sugerencia
| *Cuando cumple el objetivo*
|===

* Un LLM solo *predice texto*: no actúa, no ve el mundo, no recuerda entre sesiones.
* Un *agente* es un LLM con objetivo, herramientas y un bucle de decisión.

=== El bucle agéntico

[source,text]
----
 Objetivo ──▶ RAZONAR (LLM) ──▶ ACTUAR (tool) ──▶ OBSERVAR resultado
                  ▲                                        │
                  └──────────── repetir hasta terminar ◀───┘
----

* *Razonar*: el LLM decide la siguiente acción (function calling).
* *Actuar*: invoca una herramienta: `oc`, bash, leer/escribir archivos, una API.
* *Observar*: el resultado de la herramienta vuelve al contexto y alimenta la siguiente decisión.
* El bucle termina cuando el LLM decide que el objetivo está cumplido.

=== Anatomía de un agente

* *Modelo* — el cerebro: `{l4-model}` servido en la GPU L4 (en este workshop).
* *Herramientas* — las manos: terminal, `oc`, editor, APIs.
* *Contexto y memoria* — historial de conversación, resultados de tools, archivos del proyecto.
* *Orquestación* — el runtime que mueve el bucle: **OpenCode**.
* *Guardarraíles* — permisos, aprobaciones, cuotas y límites.

=== Skills: experiencia empaquetada

Un *skill* es un `SKILL.md` versionado, con instrucciones paso a paso que el agente *carga bajo demanda*.

[source,markdown]
----
---
name: enable-observability
description: Habilita la observabilidad de MaaS en este cluster
  OpenShift AI... Usar cuando el usuario pida habilitar
  observabilidad o ver el uso de tokens.
---
(instrucciones paso a paso...)
----

* `name`: el identificador con el que OpenCode invoca el skill.
* `description`: lo que el agente usa para decidir *cuándo* activarlo.
* Cuerpo: *qué hace*, paso a paso.

* Skills ≠ tools: las *tools* son funciones que el agente ejecuta; los *skills* son *conocimiento* — cómo hacer algo bien.
* Analogía: el onboarding de un empleado nuevo: le das el runbook, no reescribes su cerebro.

=== Skills en este workshop

El despliegue de OpenCode trae dos skills, copiados del repo a `~/.config/opencode/skills/`:

* *`configure-maas`*: deja OpenCode apuntando al modelo vía MaaS (gateway + API key + cuota).
* *`enable-observability`*: monta el stack completo de observabilidad (Tempo, OpenTelemetry, Loki, MinIO, usage logging) y deja los dashboards de tokens listos.

[source,text]
----
 Tú: "ejecuta el skill enable-observability"
   └─▶ OpenCode lee el SKILL.md ──▶ planifica ──▶ ejecuta
         (clona repo, bash apply-maas-observability.sh,
          espera cada operador, verifica)
----

* El cierre del círculo narrativo: *la observabilidad del sistema agéntico la monta el propio agente*.

== Bloque 3 · Servir y consumir modelos (MaaS)

=== El problema que resuelve MaaS

Sin MaaS, cada consumidor apunta *directo al pod del modelo*:

* ¿Quién consume cuánto? — *sin visibilidad ni control*
* ¿Cómo cambio de modelo sin romper a los consumidores? — *acoplamiento total*
* ¿Cómo doy acceso sin dar el cluster entero? — *sin autenticación de negocio*

=== Qué es Models as a Service

*Modelos servidos como servicio*: endpoint estable, autenticación, cuotas y métricas. El consumidor no sabe (ni le importa) dónde corre el modelo.

[cols="1,1", options="header"]
|===
| Pieza | Qué aporta
| *Gateway* | Punto de entrada único y routing entre modelos
| *API keys* | Identidad del consumidor (quién llama)
| *Cuotas / rate limiting* | Control de uso (cuánto puede llamar)
| *Publicación* | Qué modelos se exponen como servicio
|===

=== Servir el modelo: KServe → llm-d

El cluster trae *dos motores de serving*:

[cols="1,1,1", options="header"]
|===
| | *KServe* (el clásico) | *llm-d* (el nuevo)
| Recurso | `InferenceService` | `LLMInferenceService`
| En este lab | `{base-model}` (pre-desplegado) | `{l4-model}` (módulo 4)
| Debajo | ServingRuntime genérico | vLLM sobre Gateway API
|===

* Detalles del despliegue llm-d que importan para el resto del workshop:
* `max-model-len=8192` — contexto suficiente para OpenCode.
* `--enable-force-include-usage` — obliga a vLLM a reportar *usage* (tokens) en cada respuesta: sin esto, no hay métricas de uso en MaaS.
* HTTPS end-to-end: el pod monta el cert que el gateway usa para re-encriptar.

=== El hardware: GPU L4 y cuantización

* *NVIDIA L4* — GPU de *inferencia* (ada-lovelace): en el sandbox, un `g6.8xlarge` con 1 GPU.
* *AWQ INT4* — el Qwen3-14B cuantizado ocupa ~5.5 GB: cabe en la L4 con margen, rápido y con contexto para OpenCode.
* 1 GPU, *un modelo a la vez*: por eso el módulo 4 *detiene* el modelo base (stop nativo de KServe) antes de desplegar el nuevo.
* Trade-off de la cuantización: menos memoria y más throughput, ligera pérdida de precisión.

=== Kuadrant / Connectivity Link: auth y límites

Debajo del gateway MaaS está *Kuadrant* (Red Hat Connectivity Link):

[cols="1,1", options="header"]
|===
| Componente | Qué hace
| *Authorino* | Autenticación/autorización: valida la API key en cada request
| *Limitador* | Rate limits y cuotas: cuántos tokens puede consumir cada key
| *Gateway API* | Routing y policies declarativas (el sucesor de Ingress)
|===

* *Gateway API* ≠ Ingress: recursos (`Gateway`, `HTTPRoute`) con routing por header/path y policies anexadas.
* El gateway MaaS (`maas-default-gateway`) es un recurso Gateway API con Postgres detrás (estado del gateway).

=== MaaS en este cluster

[source,text]
----
 OpenCode ──▶ Gateway MaaS (auth + cuota) ──▶ {l4-model} (llm-d, GPU L4)
                  │
                  └── Kuadrant (Authorino + Limitador) + Postgres
----

* Módulo 3: *habilitar MaaS* — GatewayClass, Istio, Kuadrant, Postgres y el gateway, encendido en el `DataScienceCluster`.
* Módulo 4: *publicar el modelo* — `{l4-model}` en la L4 con `LLMInferenceService` (llm-d), adjuntado al gateway de MaaS con auth real y subscription.
* Módulo 5: *consumirlo* — OpenCode llama al gateway con su API key y su cuota.

=== API keys y cuotas en la práctica

* Creas la key en *RHOAI → Models as a Service → API keys* (o por API con tu token de OpenShift).
* La key *identifica al consumidor*: sin ella no hay auth, ni cuotas, ni métricas de uso.
* *Subscription* con cuotas de tokens asociada al modelo publicado.
* La key se inyecta en el `ConfigMap` de OpenCode (módulo 5) y atraviesa todo: acceso, uso y observabilidad.

== Bloque 4 · Observabilidad: logs, métricas y trazas

=== ¿Por qué observar un sistema agéntico?

* *No determinista*: la misma pregunta, dos veces, dos caminos distintos.
* *El coste se mide en tokens*: sin visibilidad, factura ciega.
* *El fallo es sistémico*: agente → gateway → modelo; ¿dónde se rompió?
* *"No puedes gestionar lo que no puedes medir."*

=== Pilar 1: Logs

*Qué pasó* — eventos con detalle, a posteriori.

* En LLM/MaaS: *usage logging* — prompt, completion y *tokens por petición*, por API key.
* Logs de inferencia y de los componentes del stack.
* En este workshop: **Loki + MinIO** (usage logging de MaaS).
* Responde: *"¿qué consumió esta API key ayer?"*

=== Pilar 2: Métricas

*Cuánto y cómo de rápido* — números agregados, series temporales.

* Del LLM: *tokens/s*, *TTFT* (time to first token), latencia p95, tasa de error, requests.
* Del negocio: *tokens por API key*, por modelo, por día.
* En este workshop: **OpenTelemetry** + dashboards **Perses** en RHOAI (y Prometheus user-workload scrapeando el modelo).
* Responde: *"¿cómo de rápido y cuánto cuesta?"*

=== Pilar 3: Trazas

*El camino completo* — una petición de extremo a extremo, cruzando componentes.

[source,text]
----
 span: agente (razonamiento) ─┐
                              ├──▶ una petición, un trace
 span: gateway (auth+cuota) ──┤
                              │
 span: modelo (inferencia) ───┘
----

* En este workshop: **Tempo** (con OpenTelemetry).
* Responde: *"¿dónde se rompió y dónde va el tiempo?"*

=== Los tres pilares, juntos

[cols="1,1,1", options="header"]
|===
| Pilar | Pregunta | En este workshop
| *Logs* | ¿Qué pasó? | Loki + MinIO (usage logging)
| *Métricas* | ¿Cuánto y cómo de rápido? | OpenTelemetry + dashboards Perses
| *Trazas* | ¿Por dónde fue? | Tempo
|===

* El flujo típico: *métrica* (alerta) → *traza* (dónde) → *log* (detalle).
* Correlación por API key / request id: las tres vistas se cruzan.

=== El stack de observabilidad del workshop

El skill `enable-observability` (módulo 6) monta, con OpenCode como agente:

. *Tempo*, *OpenTelemetry* y *Cluster Observability Operator*
. *Loki* + *MinIO* y `LokiStack` (usage logging)
. Telemetría del gateway MaaS (`maastenantconfig`) y `usageLogging` en el `DataScienceCluster`
. Dashboards de tokens en RHOAI
