= Cluster pre-desplegado

Este es el ambiente de partida, *siempre igual*: un sandbox OpenShift con OpenShift AI instalado, una GPU L4 y un modelo `{base-model}` pre-configurado. Antes de tocar nada, verificamos la base.

== Verificar OpenShift AI

[source,bash]
----
oc get dsc default-dsc
oc get pods -n redhat-ods-applications | head
----

El `DataScienceCluster` debe estar en `Ready` (RHOAI {rhoai-version}).

== Verificar la GPU L4

[source,bash]
----
oc get nodes -l nvidia.com/gpu.product=NVIDIA-L4 -o name
oc get pods -n nvidia-gpu-operator | grep gpu-operator
----

Debe existir al menos un nodo con `NVIDIA-L4` (en el sandbox: `g6.8xlarge`, 1 GPU, ada-lovelace).

== Verificar el modelo base `{base-model}`

El modelo pre-configurado es `{base-model}` servido con *KServe* (no llm-d), en el proyecto `my-first-model`:

[source,bash]
----
oc get isvc,servingruntime -n my-first-model
----

`InferenceService/llama-32-3b-instruct` debe estar `Ready`.

CAUTION: Si tu cluster pre-desplegado trae el modelo con otro mecanismo, identificalo con `oc get isvc,servingruntime,llminferenceservice -A` y adapta el módulo 2 para borrarlo y liberar la GPU.

== Verificar Gateway API y Authorino (pre-instalados)

El controller de Gateway API ya está activo (RHOAI/llm-d): `istiod-openshift-gateway` corre en `openshift-ingress` y existen las GatewayClasses `data-science-gateway-class` y `openshift-ai-inference`:

[source,bash]
----
oc get gatewayclass
oc get pods -n openshift-ingress
----

El Operator de *Authorino* viene pre-instalado globalmente:

[source,bash]
----
oc get csv -n openshift-operators | grep authorino
----

NOTE: Al instalar Connectivity Link (módulo 6), OLM reutiliza este Authorino pre-instalado. Si OLM reporta `constraints not satisfiable`, desinstala primero la subscription pre-instalada de Authorino y deja que Connectivity Link traiga su propia versión.

== Instala los operadores

El workshop depende de dos operadores de Red Hat que *deben estar instalados* en el cluster:

* *Red Hat Connectivity Link* (`rhcl-operator`): provee Kuadrant (Authorino + Limitador), la base de MaaS y de las policies del gateway.
* *Leader Worker Set* (`lws-operator`): orquesta los pods de inferencia llm-d (requerido para despliegues con paralelismo multi-nodo).

Verifica que estén instalados:

[source,bash]
----
oc get csv -A | grep -Ei "connectivity-link|leader-worker-set"
----

Ambos CSV deben aparecer en estado `Succeeded`.

CAUTION: Los operadores *Red Hat Connectivity Link* y *Leader Worker Set* deben estar instalados antes de empezar: sin Connectivity Link, MaaS (módulo 6) no puede instalar Kuadrant; sin Leader Worker Set, los despliegues llm-d (módulo 3) no se crean. Si falta alguno, instalalo desde OperatorHub:

* *Red Hat Connectivity Link*: paquete `rhcl-operator`, canal `stable`, en el namespace `kuadrant-system`:

[source,bash]
----
oc new-project kuadrant-system
oc apply -f - <<EOF
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: kuadrant
  namespace: kuadrant-system
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhcl-operator
  namespace: kuadrant-system
spec:
  channel: stable
  installPlanApproval: Automatic
  name: rhcl-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF
----

* *Leader Worker Set*: operador `Leader Worker Set Operator`, canal `stable-v1.0`, en el namespace recomendado `openshift-lws-operator`. Requiere el Operator de *cert-manager* para Red Hat OpenShift instalado:

[source,bash]
----
oc new-project openshift-lws-operator
oc apply -f - <<EOF
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: lws-operator
  namespace: openshift-lws-operator
spec:
  channel: stable-v1.0
  installPlanApproval: Automatic
  name: lws-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF
----

Después de instalar Leader Worker Set, crea la instancia del CR `LeaderWorkerSetOperator` (Installed Operators → Leader Worker Set Operator → *Create instance*).

Espera a que los pods de ambos operadores estén `Running`:

[source,bash]
----
oc get pods -n kuadrant-system
oc get pods -n openshift-lws-operator
----

== Preparar el certificado del gateway de inferencia

El gateway de inferencia de la plataforma (`openshift-ai-inference`, que expone los modelos en `inference-gateway.apps.<domain>`) referencia un cert TLS que el provisionador puede no crear. Sin cert, el TLS handshake cuelga y los requests al modelo no responden.

Verifica:

[source,bash]
----
oc get secret default-gateway-tls -n openshift-ingress
----

Si **no existe**, crealo con el cert default del ingress (cubre `*.apps.<domain>`) y reinicia el proxy del gateway:

[source,bash]
----
CERT=$(oc get ingresscontroller default -n openshift-ingress-operator \
  -o jsonpath='{.spec.defaultCertificate.name}')
oc get secret ${CERT} -n openshift-ingress -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/gw-tls.crt
oc get secret ${CERT} -n openshift-ingress -o jsonpath='{.data.tls\.key}' | base64 -d > /tmp/gw-tls.key
oc create secret tls default-gateway-tls -n openshift-ingress --cert=/tmp/gw-tls.crt --key=/tmp/gw-tls.key
oc delete pod -n openshift-ingress -l gateway.networking.k8s.io/gateway-name=openshift-ai-inference
----

Verifica que responde:

[source,bash]
----
curl -sk -o /dev/null -w "%{http_code}\n" --max-time 10 \
  https://inference-gateway.apps.$(oc get ingresses.config/cluster -o jsonpath='{.spec.domain}')/health
----

`200` = listo. Es un paso *one-time por sandbox*.

== Verificar que MaaS *no* está encendido

[source,bash]
----
oc get dsc default-dsc -o jsonpath='{.spec.components.aigateway}' 2>/dev/null; echo
oc get ns | grep -Ei "kuadrant|gateway-infra" || echo "sin MaaS ni Kuadrant"
----

En este punto `aigateway` está vacío o en `Removed`, y no existe `kuadrant-system` ni `redhat-ai-gateway-infra`. Los módulos 5–6 los crean.
